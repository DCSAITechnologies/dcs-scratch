# Connector data sourcing: 4 parallel terminals

**सार (Hindi):** 809 published connectors में कुछ data missing है (logo, website / dev-docs / API-docs links, auth, tools, permission scopes). यह काम 4 हिस्सों (part-1 … part-4) में बँटा है। हर हिस्से में लगभग 200 connectors हैं। 4 terminals खोलें, हर terminal में नीचे वाला prompt paste करें (सिर्फ `PART=` बदलें)। हर terminal अपनी `data-sourcing/returns/part-N/` folder बनाएगा। चारों पूरे होने पर `data-sourcing/returns/` को zip करके मुझे भेज दें, या push कर दें (§5)। फिर मैं validate और merge करूँगा।

Nothing here is guessed. Every fact needs an official source URL. A fact without one is rejected automatically.

**How the work is split.**
- The split is by connector, not by field.
- One terminal does every field for its own ~200 connectors. It reads each provider's docs once: the same pages give the links, the auth method, the scopes and the operations.
- All connectors from one provider (for example everything from Google or Atlassian) stay in the same part.
- The parts are balanced by the number of missing facts.

## 2. Where the data comes from (in priority order)

1. **Connector OS core manifests (best source for tools and scopes).**
   - Core's per-connector manifests (`packages/connectors/<id>/manifest.json` in the core repository) define the connector's real tools and scopes.
   - They were not in the 4 core packs.
   - If you can export that folder as a zip, send it. It fills tools and scopes exactly, and Terminals 1–4 then only need logos and links.
2. **The provider's own official pages:**
   - website
   - developer portal
   - API reference
   - auth / OAuth scopes page
   - status page
   - press kit / brand page (for logos)
3. **Accepted third-party hosts**, only when the provider itself links to them as its official docs or status page:
   - GitHub
   - readme.io / gitbook.io / Postman / Stoplight / SwaggerHub
   - statuspage.io and similar status hosts
   - Wikimedia Commons, for logos only

**Never use:**
- blogs
- aggregators (RapidAPI, Zapier pages, G2, Crunchbase)
- AI answers
- guesses
- your memory

## 4. The prompt (paste into each terminal, change only the first line)

```text
PART=1

You are filling connector facts for the Connector OS website. Work only from official sources.

INPUT
- data-sourcing/inputs/part-${PART}.csv : one row per connector.
  The `needs` column lists which facts are missing (logo; site; portal; api; authDocs; whDocs; statusUrl; auth; caps; scopes; reqs).
  Columns site/portal/api/... show what we already have (use them as starting points; do not repeat them).
  core_read_tools / core_write_tools = how many tools core's connector has (context only).

OUTPUT (write only inside data-sourcing/returns/part-${PART}/)
- records.jsonl : exactly ONE JSON object per line for EVERY id in the CSV (also when nothing was found).
- logos/<id>.svg or logos/<id>.png : downloaded logo files.

RECORD FORMAT (omit any field you could not confirm; never write null/placeholder text)
{
  "id": "<id from csv>",
  "checked": "YYYY-MM-DD",
  "site": "https://...",            // official homepage
  "portal": "https://...",          // developer portal / docs home
  "api": "https://...",             // API reference
  "authDocs": "https://...",        // page describing authentication / OAuth scopes
  "whDocs": "https://...",          // webhooks docs (only if the csv says webhooks=yes or the provider documents webhooks)
  "statusUrl": "https://...",       // official status page
  "auth": "OAuth 2.0",              // EXACTLY one of: OAuth 2.0 | OAuth 2.0 + PKCE | OAuth 2.0 Client Credentials | API Key | API Key (multiple headers) | Bearer Token | HTTP Basic | App password session | Provider-signed JWT | None (public API) | Provider-specific
  "scopeModel": "oauth_scopes",     // EXACTLY one of: oauth_scopes | api_key_permissions | account_roles | none
  "providerScopes": [ {"scope": "read:orders", "access": "read", "purpose": "Read orders"} ],   // access = read | write | admin; max 80; copy scope strings exactly as documented
  "providerCaps": [ {"name": "List orders", "access": "read", "endpoint": "GET /v1/orders"} ], // access = read | write; 5-25 main operations; max 60
  "reqs": ["A <Provider> account on a plan with API access", "An API key created in Settings → API"],  // max 8 short lines, only what the docs say
  "logo": {"file": "logos/<id>.svg", "source": "https://<provider page the file came from>"},
  "evidence": {                     // REQUIRED for every non-link fact you include
    "auth": "https://<page that states the auth method>",
    "scopes": "https://<page listing the scopes/permissions>",
    "caps": "https://<API reference page listing the operations>",
    "reqs": "https://<page stating the requirements>"
  },
  "notFound": ["statusUrl"],        // facts you looked for and could not confirm
  "notes": "optional, short"
}

RULES (the ingest script enforces these; violations are rejected)
1. Official sources only: the provider's own domain, or a docs/status host the provider itself links to (GitHub, readme.io, gitbook.io, Postman, Stoplight, SwaggerHub, statuspage.io). Wikimedia Commons is accepted for logos only.
2. Every URL must be https, must open (HTTP 200 after redirects), and must be the specific page, not a search result.
3. Never invent. If unsure, leave the field out and add it to notFound. Do not copy facts from another connector by the same provider unless that page covers this product.
4. Scopes: copy the exact strings from the provider's scope list. For API-key products, set scopeModel "api_key_permissions" and list documented key permissions if there are any; otherwise leave providerScopes out.
5. Capabilities describe the provider's API (what it supports), not what our connector does. Use plain names ("List invoices", "Create a contact") plus the documented method+path when shown.
6. Logos: prefer the provider's press/brand kit or the SVG used in its website header; the square icon/mark beats the wide wordmark. SVG preferred; PNG must be at least 64x64. Never redraw, recolour, crop from a screenshot or generate a logo. Max 200 KB. No <script> in SVG.
7. Do not change any other file in the repo.

PROCEDURE (target: 30–45 minutes)
- Split the CSV into batches of about 25 connectors and process batches in parallel with subagents (about 8 at a time). Each subagent returns JSON lines; you append them to records.jsonl.
- For each connector: open the existing site/portal link first, then find the API reference, the auth page, the scopes page, the status page (often status.<domain>), and the brand/press page.
- Download logos with curl into data-sourcing/returns/part-${PART}/logos/.
- When done, run:  python3 scripts/ingest-sourced-data.py --dry-run
  Fix every rejection that is a mistake (wrong domain, bad enum, missing evidence). Rejections where no official source exists are fine: leave the field out.
- Finish with a short summary: records written, facts per field, rejections left and why.
```

## 6. What happens after (I run this)

```bash
python3 scripts/ingest-sourced-data.py     # validates; writes src/lib/sourced-data.json, public/logos/sourced/*, data-sourcing/INGEST_REPORT.md
npm run sync:catalogue                     # fills ONLY empty fields; core + editorial records always win
npm run verify                             # build, gates, e2e, axe
```

What the ingest step guarantees:
- **Fill-empty only.** A sourced fact never overwrites core or a curated editorial record. For example, if core says "API Key", a sourced "OAuth 2.0" is not applied.
- **Labelled as provider facts.** Provider capabilities and scopes appear on the connector page as "What the <Provider> API supports" and "Permission scopes documented by <Provider>", each with its source link and check date. They are kept separate from core's connector tools, so nothing reads as a runtime claim.
- **Traceable and reversible.**
  - Every applied fact keeps its evidence URL in the catalogue row (`sourced.evidence`).
  - Deleting `src/lib/sourced-data.json` and re-running sync restores the previous catalogue exactly.
- **Rejected facts** are listed with a reason in `data-sourcing/INGEST_REPORT.md`, so they can be fixed and re-run.
